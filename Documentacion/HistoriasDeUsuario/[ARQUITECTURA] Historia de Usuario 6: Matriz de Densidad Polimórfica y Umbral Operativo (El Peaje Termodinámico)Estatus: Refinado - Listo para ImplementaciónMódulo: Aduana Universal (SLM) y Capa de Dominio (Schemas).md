[ARQUITECTURA] Historia de Usuario 6: Matriz de Densidad Polimórfica y Umbral Operativo (El Peaje Termodinámico)Estatus: Refinado - Listo para ImplementaciónMódulo: Aduana Universal (SLM) y Capa de Dominio (Schemas)1. Descripción GeneralComo Arquitecto de Software y guardián de la integridad lógica del sistema,Quiero estructurar la extracción de información del usuario mediante un Catálogo de Matrices de Densidad (Patrón Registry) gobernado por un esquema estricto (Zod) y un umbral de supervivencia (60%),Para garantizar que el motor principal (LLM) no alucine por falta de contexto cronológico, al mismo tiempo que el código base queda abierto a la inserción futura de nuevas matrices temáticas sin alterar la base de datos vectorial ni el motor de enrutamiento.2. Justificación Arquitectónica (Vía del Yunque y OCP)Aplicando el Principio de Abierto/Cerrado (OCP) de la directriz S.O.L.I.D., la definición de la información a extraer no puede ser un monolito rígido. El sistema requiere un Patrón Envelope (Envoltorio) que permita al agente ligero (SLM) y al motor vectorial procesar diferentes tipos de datos. Todo ello blindado por el Filtro A (Lógica) que dicta que la Ventana Temporal es el único parámetro de supervivencia bloqueante; si el orquestador desconoce el tiempo, la física de cruzar distancias con horarios de cierre se destruye.   3. Coreografía de la Matriz Polimórfica y Pesos TermodinámicosEl diseño se despliega en dos capas (Definición e Instanciación):A. El Contrato de Dominio (Zod Discriminated Union):
En src/domain/schemas/matrix.ts, se define el catálogo evitando el uso de tipos any. Cada matriz instanciada contiene un envoltorio estándar:   matrix_id: Identificador técnico (ej. "default").name: Nombre legible (ej. "Exploración Urbana Base").description: Instrucción incrustada para el LLM pesado (ej. "Matriz logística para itinerarios generales diurnos").payload: El objeto tipado con los datos extraídos.B. Pesos de la Matriz "Default" (Umbral Adaptativo):Vector A: Supervivencia Cronológica (60%) [Bloqueante]: time_window (Marcas temporales exactas ISO 8601).Vector B: Enriquecimiento Táctico (40%) [Opcional]: group (15% - size y type), vibe (15% - enumeraciones de ambiente), y constraints (10% - presupuesto, dieta, movilidad reducida).C. Persistencia Vectorial con Metadatos:
El JSON validado por Zod se inyecta en LanceDB. El campo matrix_id se extrae y se almacena como metadato indexable del vector, permitiendo al RAG aislar contextos si el usuario cambia de matriz en futuras interacciones de la misma sesión.   4. Criterios de Aceptación (Verificación Empírica)Escenario 1: Blindaje del Dominio y Generación de EsquemaDado el archivo de esquemas en la capa de dominio src/domain/schemas/matrix.ts.   Cuando el desarrollador compila el código o exporta el esquema mediante Zod a JSON Schema.Entonces el compilador de TypeScript verifica que no existen tipos any.   Y el JSON Schema resultante exige obligatoriamente los campos matrix_id, name, description y un payload estructurado antes de validar la entrada.Escenario 2: Desbloqueo del Umbral y Fricción CeroDado el SLM (Aduana Universal) operando con la matriz "default".Cuando el usuario indica "Tengo todo el sábado libre", proporcionando únicamente el time_window (60%).Entonces la UI desbloquea inmediatamente el botón de "Forjar Ruta" (Fricción Cero).   Y el conserje transparente la situación: "Tengo el tiempo fijado. Puedo montarte el itinerario ya mismo asumiendo un ritmo estándar, o si me dices cuántos sois y qué rollo buscáis, lo calibro mejor."Escenario 3: Bloqueo de Supervivencia Logística (< 60%)Dado un usuario que inicia el diálogo pidiendo "Somos 4 personas buscando tapas baratas" (Grupo 15% + Restricciones 10% = 25%).Cuando el SLM evalúa el progreso de la matriz.Entonces el botón de ejecución permanece inactivo y el payload no se libera al motor principal.Y el agente ligero intercepta conversacionalmente la variable bloqueante: "Perfecto, plan de tapas para cuatro. Para encajar las reservas y los paseos, ¿qué días o cuántas horas tenéis libres?"Escenario 4: Recuperación Polimórfica (RAG)Dado un usuario que ha generado historiales en LanceDB etiquetados con el metadato matrix_id: "default".   Cuando el orquestador principal ejecuta la consulta RAG pre-ejecución.Entonces LanceDB recupera el payload de alta densidad.Y el orquestador inyecta la propiedad description de la matriz en el system prompt del LLM pesado, calibrando su comportamiento cognitivo antes de procesar los horarios y los aforos de la base de datos estática.
